# IntakeFlow - CRM Landing Page & AWS Lambda Deployment Guide

## Overview

Welcome to the **IntakeFlow Landing Page** repository. IntakeFlow is a SaaS application functioning as a Lead Management System (CRM). This landing page serves as the primary touchpoint for potential clients to contact us and understand our services. 

This repository contains the front-end application built with **React, Vite, and TanStack Start (SSR)**, tailored using Lovable.

A key feature of this repository is its optimized deployment strategy: it is configured to run fully Server-Side Rendered (SSR) on **AWS Lambda**. This guide provides a comprehensive, step-by-step walkthrough of transforming this codebase into a production-ready AWS Serverless artifact, bypassing manual IaC complexities for quick deployment.

---

## Prerequisites

Before starting the deployment process, ensure you have the following configured locally:

1. **Node.js** (v18+ recommended) and `npm`.
2. **AWS CLI** installed and configured with appropriate credentials (e.g., a profile named `devops`).
3. **WSL (Windows Subsystem for Linux)** or a Unix-like terminal (strongly recommended for optimal zipping).
4. An **AWS S3 Bucket** created in the *exact same region* where you intend to deploy your Lambda function.

## Step-by-Step Deployment Guide

Follow these steps carefully to build, package, and deploy the application.

### 1. Local Setup & Build

First, clone the repository and build the production assets.

```bash
# 1. Clone the repository
git clone <repository-url>
cd intakeflow-landing

# 2. Install dependencies
npm install

# 3. Build the project
# This generates the `dist` folder containing `client` (static assets) and `server` (SSR entry).
npm run build
```
###  2. Prepare the Lambda Artifact

AWS Lambda has strict size limits (50MB zipped / 250MB unzipped). Since the application relies on the fetch API output generated by Nitro for Cloudflare, we must use a custom bridge (lambda.mjs) and isolate only production dependencies.
```bash 
# 1. Clean up any previous build artifacts
rm -rf lambda_build deploy.zip

# 2. Create a temporary staging directory
mkdir lambda_build

# 3. Copy the necessary compiled files and configurations
cp -r dist lambda_build/
cp lambda.mjs lambda_build/
cp package.json lambda_build/
cp package-lock.json lambda_build/

# 4. Install strictly production dependencies to keep the size minimal
cd lambda_build
npm ci --omit=dev

# 5. Compress the artifact using maximum compression (-9)
# This is crucial to ensure the zip file stays under the 50MB direct upload limit if possible.
zip -r -9 ../deploy.zip *

# 6. Clean up the temporary staging directory
cd ..
rm -rf lambda_build
```
### 3. Upload to Amazon S3

Due to network timeouts often encountered when uploading larger files directly via the AWS Console, it is highly recommended to upload the artifact to an S3 bucket first.   Crucial Tip: The S3 bucket MUST be in the same AWS Region as your target Lambda function
``` bash
# Upload the zip file to your S3 bucket
# Replace <YOUR_BUCKET_NAME> with your actual bucket name.
aws s3 cp deploy.zip s3://<YOUR_BUCKET_NAME>/SSR_Applications/deploy.zip --profile devops
```
### 4. Create and Configure the AWS Lambda Function
Now, update or create your Lambda function to use the uploaded code.   

```bash
# Update the Lambda function code using the S3 object
# Replace <YOUR_FUNCTION_NAME> and <YOUR_BUCKET_NAME> accordingly.
aws lambda update-function-code \
    --function-name <YOUR_FUNCTION_NAME> \
    --s3-bucket <YOUR_BUCKET_NAME> \
    --s3-key SSR_Applications/deploy.zip \
    --profile devops
    ```
```
## Essential Lambda Configurations (Via AWS Console or CLI)
Once the code is uploaded, you must configure the runtime settings to ensure the Lambda function routes requests correctly and doesn't timeout during SSR processing.  

1 - Update the Handler:
Navigate to Runtime settings -> Edit.  
Change the Handler to: lambda.handler 
 Why? AWS expects [filename].[functionName]. Our bridge file is lambda.mjs and exports const handler
 
 2 .   Adjust Timeout and Memory:
 Navigate to Configuration -> General configuration -> Edit[cite: 1].
 Timeout: Increase to at least 30 seconds[cite: 1]. The default 3 seconds is insufficient for SSR[cite: 1].
 Memory: Increase to at least 512 MB (1024 MB recommended for faster execution)[cite: 1]. Lambda allocates CPU power proportionally to memory; 128MB will result in very slow rendering[cite: 1].
 
 3 - Environment Variables:If your application uses external services (like Google Apps Script for the contact form), ensure those URLs are added as Environment Variables in the Lambda configuration (e.g., VITE_GOOGLE_SCRIPT_URL)[cite: 1].

## 5. Final Verification
After saving the configurations, test your Lambda Function URL or API Gateway endpoint[cite: 1]. The SSR application should now be fully operational, rendering styles correctly and successfully submitting forms[cite: 1].

Understanding the lambda.mjs Bridge
The lambda.mjs file in the root directory is the core of this deployment strategy[cite: 1]. It performs two critical functions:

Static Asset Serving: It intercepts requests for static files (.png, .css, .js) and serves them directly from the dist/client directory, applying the correct MIME types[cite: 1].

SSR Request Translation: Since the Lovable/Nitro build outputs a Web Fetch API handler (designed for Cloudflare), lambda.mjs translates the incoming AWS Lambda event into a standard Web Request object, passes it to the TanStack SSR fetch handler, and translates the output back into an AWS Lambda compatible response[cite: 1]. It explicitly handles header edge cases (like undefined host) to prevent TypeError crashes[cite: 1].
